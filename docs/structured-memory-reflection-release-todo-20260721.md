## 1. 项目位置与本模块的论文角色

论文主线是面向 STS2 的超长序列、分层决策 Benchmark。它要研究提示词、上下文组织、形式化状态、路线规划、后验选牌、结构化记忆等机制在完整游戏中的真实作用。

结构化记忆与反思只是一项可消融模块，目标不是：

- 把论文改写成一篇通用记忆系统论文；
- 穷举 STS2 的战斗、卡牌、敌人和路线知识；
- 依靠人工规则彻底解决 STS2；
- 用复杂工程掩盖模型无法提取或使用经验的事实。

本模块需要做到：

1. 从完整长轨迹中产生可追溯的结构化经验；
2. 在自然游戏过程中检索并注入经验；
3. 根据注入后的新轨迹审视、修改、合并、晋升或拒绝经验；
4. 让模型能力、经验质量、检索策略和最终表现之间的关系可以被实验分析；
5. 如果机制不工作，也能给出可信的失败原因，而不是继续堆代码。

## 2. 本计划依据的讨论结论

以下约定按时间和后续修正关系整理。后出现的明确修正覆盖早期方案。

### 2.1 不再变化的上层结论

- 七月底 AAAI 投稿是时间边界，Benchmark 是主贡献，记忆不是主落点。
- Baseline 行为、完整上下文和 CoT 路线语义不得因记忆模块而改变。
- 经验语言与英文游戏和英文 Baseline 保持一致；中文只用于面向用户的报告。
- 卡牌、升级、遗物、敌人、地图、合法动作等信息必须完整提供，不得以加速或压缩为由删除。
- 正式结论来自完整游戏；Mini 场景只验证工程契约或提供 Case Study。
- 不得把“经验进入提示词”“动作发生变化”或“测试通过”单独写成性能提升。

### 2.2 经验来源与反思粒度

- 经验来自真实完整轨迹，而不是人工撰写反思谱。
- 战斗结束：审视本场战斗及本场实际注入的经验，同时允许产生战斗、卡牌、路线或通用经验。
- 每幕结束：重点审视路线和跨战斗资源后果，同时允许跨域产出。
- 每局结束：重点审视完整选牌序列、整局路线、牌组演化和全局战斗风格，同时允许跨域产出。
- 在线反思同时包含两类操作：生成新经验；审视已有经验。
- 首局从空库开始时可能没有注入，但必须能产生经验；后续自然命中才构成真实验证。

### 2.3 候选、验证与融合

- 模型生成的原始候选必须完整保存，不能在报告前由人工或程序挑选“好看的几条”。
- 新经验先进入 Pending；后续真实暴露可以产生支持、反驳、修订、合并、晋升或拒绝。
- 生产流程不依赖人工读档重打。回放只用于调试和 Mini 契约验证。
- 同一检索条件下的重复或近义经验应由反思模型合并压缩；不能用“每场只投递一次”或硬 Top-K 掩盖重复污染。
- 反思节点允许产生其他领域的经验，不能因为节点名称是 combat 就丢弃 card 或 route 候选。

### 2.4 最新且优先级最高的语义边界

- Python 只负责系统正确性：格式、字段类型、引用、完整上下文、身份、事务和日志。
- 经验是否浅层、是否有信息增益、标签是否合理、是否值得晋升、是否应该融合，原则上由模型处理。
- 模型错误归类、错误理解、错误合并或错误晋升是科研观测，不是默认需要新增 Python 分支的工程 Bug。
- 只有当错误来自缺失上下文、错误提示词、错误证据绑定或程序未按协议执行时，才属于工程问题。

## 3. 对此前工作的批评与根因

### 3.1 已确认的过程错误

1. **把账本自洽当成机制正确。**

   严格审计只能证明程序按照自身规则运行，不能证明经验正确、有价值或能够改善决策。

2. **把模型语义错误逐条工程化。**

   每出现一次错误经验、错误标签或错误修订，就增加一个正则、白名单、兼容矩阵、特殊审计或回退分支，最终形成无法穷举的手写语义验证器。

3. **没有守住系统层、模型层和科研评估层的边界。**

   本应作为离线指标的“信息增益、浅层重述、幻觉、门控合理性”被写进在线准入代码，直接改变了 treatment。

4. **在最小链路尚未闭合时启动长跑。**

   先跑完整游戏、再在运行中发现生成、修订、融合、注入或审计 Bug，导致数小时实验反复作废。

5. **没有设立工程停损点。**

   当一个简单模块不断需要新增 fallback、reason code、严格审计和特殊恢复时，没有及时停止并重新检查抽象。

6. **把工作量当成进度。**

   大量代码和测试主要证明复杂规则的内部一致性，没有回答“经验是否被正确产生、自然暴露和有效使用”。

7. **没有持续核对历史约定。**

   同门控融合、修订而非直接拦截、跨域产出等已讨论功能曾被漏实现，却在中间汇报中被当作已完成。

8. **实验变量混杂。**

   经验质量、门控宽窄、在线更新、随机策略分叉和 Baseline 状态同时变化，导致无法归因。

9. **进展汇报缺少科研验收。**

   “反思调用成功”“审计通过”“有若干次注入”被过早当成有效进展，没有同步说明经验质量、真实暴露和可比结果是否成立。

### 3.2 跑偏发生的关键节点

- 在藏宝图、预备打击等错误经验出现后，正确修复应是补全卡牌事实和改善模型审计提示；实际却开始增加语义硬门控。
- 在 Pending 修订、卡牌审计和账本恢复出现冲突后，继续为每个组合增加分支，而不是质疑整套语义裁判架构。
- 在零注入或极低注入出现后，一边放宽门控、一边增加更多价值准入，造成“过严”和“过宽”在同一实现内互相修补。
- 在每幕审查和完整性需求出现后，把科研人工检查升级成 HMAC、外部审批和数千行严格审计，偏离了最小科研框架。

### 3.3 这次必须吸取的结论

如果模型在完整证据和合理提示下仍然产生垃圾经验，这就是 RQ1 的结果；如果模型生成错误检索标签并导致错误注入，这就是 RQ2 的结果；如果跨角色经验导致负迁移，这就是 RQ3 的结果。不能再用 Python 把这些现象提前过滤掉。

## 4. 三层职责边界

以后每一项检查或功能必须先归入以下一层。无法归类时不得直接实现。

| 层 | 负责内容 | 允许阻断运行 | 不允许承担 |
|---|---|---:|---|
| 系统层（Python） | 完整上下文、JSON/schema、ID 引用、事务、版本、日志、可复现配置、提示拼装 | 是 | 判断经验正确、深刻、有价值或适用 |
| 模型层（同一 LLM） | 产生经验、给出检索键、审视证据、修改、合并、拒绝、晋升 | 否，语义错误要留下 | 静默修改系统事实或伪造证据 |
| 研究评估层 | 离线标注忠实度、幻觉、平凡性、门控质量、动作改变和表现 | 不影响 treatment | 在运行时替模型筛掉失败样本 |

### 4.1 系统层允许的失败条件

- JSON 在一次纯格式修复后仍不可解析；
- 必填字段不存在或类型错误；
- 引用了不存在的 evidence ID、memory ID 或 run ID；
- 卡牌、升级效果、合法动作或必要轨迹因程序错误未完整提供；
- API、存储或事务失败；
- 实验配置、Baseline 哈希或上下文哈希与预注册值不符；
- 提示实际未包含声明已注入的经验。

### 4.2 系统层不得阻断的内容

- 经验只是牌面重述或浅层推理；
- 模型误解卡牌、敌人或路线；
- 模型把经验分错领域或打错标签；
- 模型提出过宽、过窄或不可迁移的检索条件；
- 模型错误地 pass、revise、merge、reject 或 promote；
- 两条经验语义冲突但模型没有正确处理。

这些内容必须进入日志和离线分析。只有能够证明是提示缺失或证据错误时，才转回工程修复。

## 5. 最小目标架构

### 5.1 最小经验条目

系统字段：

- `memory_id`
- `status`: `pending | active | rejected | superseded`
- `version`
- `created_at_checkpoint`
- `updated_at_checkpoint`
- `source_run_ids`
- `evidence_ids`
- `parent_ids` / `superseded_by`

模型字段：

- `domain`: `combat | card | route | general`
- `claim`
- `advice`
- `uncertainty`
- `retrieval_keys`：敌人名、卡牌名、粗粒度标签或空键（领域通用）

不再要求模型自报或 Python 校验：

- `would_change_decision`
- `derivable_from_visible_information`
- 固定信息增益分数
- 受控状态标签词表
- 受控路线节点兼容矩阵
- 领域报告和固定原因码全集

### 5.2 反思模型输出

每个检查点允许同时输出：

- `new_items`
- `reviews`

`reviews` 对已有经验只能引用真实 `memory_id`，操作为：

- `keep_pending`
- `promote`
- `revise`
- `merge`
- `reject`

系统验证操作是否可执行，但不判断操作是否聪明。原始响应、一次格式修复响应和最终事务全部保存。

### 5.3 反思调用

默认使用一个模型完成候选产生和语义审视。为了形成清晰消融，保留两个可配置条件：

- `single_pass`：一次调用同时生成和审视；
- `critic_pass`：同一模型追加一次检查点级批量 critic 调用。

critic 只发生在战斗末、幕末或局末，不在每个动作前调用。是否需要 critic 是实验变量，不是系统正确性的前提。

### 5.4 运行时检索与注入

默认不增加逐动作 LLM 检索调用。模型在反思时生成粗粒度 `retrieval_keys`，运行时代码只做透明的字符串/集合匹配：

- 战斗：通用战斗经验、精确敌人、模型生成的敌人标签、当前牌组或当前可用卡牌；
- 选牌：通用选牌经验、候选卡牌、当前牌组；
- 路线：路线经验、当前幕和可选节点；
- 通用经验：由模型在反思检查点增量合并成版本化短提示。

运行时代码不得判断标签是否“合理”。错误标签造成的漏检或误检属于门控实验结果。

不使用“每场只注入一次”或原始条目 Top-K。相同检索键下的重复经验由检查点级模型合并。若载荷超过 API 的硬上下文上限，系统必须记录并显式失败或进入预注册的长度控制实验，不能静默截断。

### 5.5 生命周期

1. 新经验总是进入 Pending；
2. Pending 在下一次自然命中并真实注入后获得可审视证据；
3. 模型根据证据决定继续 Pending、修改、合并、晋升或拒绝；
4. Active 继续在相关检查点接受审视，但频率低于 Pending；
5. 只有实际注入过的旧经验才能用该段轨迹作为效用证据；
6. 未注入的轨迹仍可产生新经验，但不能伪装成对旧经验的支持或反驳；
7. 不写死“支持两次必晋升”等语义阈值，所有决定和证据完整记录供离线评估。

### Phase 1：先写系统契约测试

在修改实现之前，建立以下最小失败测试：

1. 完整卡牌和升级信息确实进入反思证据；
2. 合法 JSON 和真实 evidence ID 可以创建 Pending；
3. 模型误分类或浅层经验仍被保存，不被 Python 语义拦截；
4. 非法 JSON 经一次格式修复后可恢复；
5. 不存在的 evidence ID 或 memory ID 被系统拒绝；
6. 模型 `revise/merge/reject/promote` 能被原子应用；
7. 同键经验由模型 merge 后只注入合并项；
8. 战斗检查点可以产生 card/route/general 候选；
9. 原始响应和所有候选无保留落账；
10. Baseline 无记忆路径字节级不变。

验收：

- 新测试在旧实现上暴露语义拦截或接口不匹配；
- 测试只约束系统契约，不编码 STS2 策略真值。

硬性停损：

- 如果修复需要新增 STS2 游戏语义分支，立即停止并记录为科研问题；
- 同一问题经过两次局部修复仍要求新增特殊分支，停止该方向，回到三层职责表；
- 不为让旧的语义测试继续通过而保留被否定的语义规则；
- 不在这一阶段启动 fullgame。

### Phase 3：Mini 闭环验证

Mini 场景只验证以下链路：

`完整证据 -> 模型产生候选 -> Pending -> 键匹配 -> 真实注入 -> 检查点审视 -> keep/revise/merge/promote/reject -> 日志复算`

至少包含：

- 一个正确候选；
- 一个明显浅层或错误候选，证明系统不会替模型静默过滤；
- 两条同键近义候选，证明模型 merge 可执行；
- 一个错误 memory/evidence 引用，证明系统约束有效；
- 一个跨域候选；
- 一个真实注入后的审视案例；
- 一个没有注入、因此不能审视旧经验效用的案例。

Go 条件：

- 每个模型候选都有原始记录和最终 disposition；
- 经验真正进入最终行动提示；
- 系统错误被拦截，语义错误被保留；
- 不存在静默截断、静默丢弃和隐式语义修正；
- Baseline 和完整上下文不变。

No-Go 条件：

- 任何核心操作仍依赖手写 STS2 语义判断；
- 注入日志与最终 prompt 不一致；
- 同键重复经验只能靠 Top-K 或一次性投递控制；
- 需要靠人工改候选才能跑通。

### Phase 4：最小在线自然暴露 Pilot

只有 Phase 3 Go 后才执行。

建议流程：

1. 固定一个种子，从空库运行第一局；
2. 第一局结束后保留全部生成和审视结果；
3. 使用同一自然演化经验库继续第二局；
4. 检查是否出现真实 Pending 暴露和后续审视；
5. 如果冷启动两局仍无可用暴露，停止，不扩写门控，先将其归类为抽取或检索失败。

这两局只回答系统是否具备真实在线闭环，不回答性能趋势。

每幕检查只做以下审计：

- 轨迹与终局状态完整；
- 反思请求、响应和事务完整；
- 所有候选均已记录；
- 注入与最终 prompt 一致；
- 是否出现系统 Bug；
- 语义错误单独登记为研究案例，不现场加规则。

### Phase 5：固定种子连续五局 Case Study

Pilot Go 后，按既定要求使用同一种子连续五局、在线反思、串行继承经验库。

目的：

- 观察经验库从空到有的演化；
- 观察 Pending 的自然暴露、修改、合并、晋升和拒绝；
- 观察重复污染、错误标签、错误经验和负反馈；
- 形成完整长序列 Case Study。

不把五局直接当成显著性实验。报告至少包括：

- 每局终点、幕/层、终局 HP、决策数；
- 每域新候选数、审视数、状态变化；
- retrieval、exposure、实际 injection 数；
- 每条经验的首次来源和后续命中；
- 经验注入后的动作改变实例；
- 语义错误和系统错误分开统计；
- 均值、中位数、方差和五局完整分布。

### Phase 6：论文三项正式研究

#### RQ1：长时序经验总结为什么困难

比较：

- 完整轨迹单次总结；
- 战斗/选牌/路线分段总结；
- 分段总结后整局层级审视。

保持模型、证据、schema 和输出预算一致。全部原始候选进入离线评估，指标包括忠实度、幻觉、平凡性、领域覆盖、跨层冲突和跨轨迹确认。

#### RQ2：门控与暴露如何影响表现

正式消融必须从同一个已经完成 RQ1 审计的经验快照启动，保持经验正文、状态和数量不变，只改变暴露策略：

- `G0`：无记忆；
- `G1`：同领域经验宽匹配；
- `G2`：精确敌人、卡牌或路线实体匹配；
- `G3`：精确实体加模型生成的粗粒度标签匹配；
- `G4`：可选的动作前同模型选择器，作为高成本语义门控上界；
- `G5`：长度和频率匹配的错配经验负对照。

检查点 critic、经验融合和经验正文修改不属于本组门控变量，应在生成方法或独立方法消融中处理。`G4` 必须单独报告额外调用、延迟和 token 成本，不能作为默认工程依赖。

主在线 Case Study 不冻结经验库；独立 RQ2 消融可以从同一个经验快照启动以隔离门控变量。两者必须分开命名和报告。

#### RQ3：跨角色经验迁移

区分：

- 通用事实；
- 通用策略；
- 角色条件经验；
- 牌组条件经验；
- 角色私有经验。

比较无记忆、目标角色自经验、朴素跨角色迁移和类型化迁移。负迁移本身是有效结果，不通过增加人工过滤规则掩盖。

## 8. 实验归因和报告规则

### 8.1 可写成结论的最低条件

- 有真实 treatment exposure；
- Baseline 和 treatment 在首次暴露前的上下文关系可审计；
- 多 seed 或多重复形成分布级趋势；
- 行为改变、局部收益和 run-level 结果分别报告；
- 系统 Bug 样本不进入科研统计；
- 模型语义失败样本必须进入科研统计或 Case Study。

### 8.2 不能写成结论的内容

- 一两局的正向或负向差异；
- 首局冷启动零注入；
- “测试全部通过”；
- “产生了若干经验”；
- “注入次数很多”；
- “模型在 reason 中引用了经验”；
- 处理前上下文已经随机分叉的单个配对结果。

### 8.3 Fullgame 与 Case Study 同时保留

- Fullgame 分布回答总体趋势；
- 自然 Case Study 回答经验如何产生、命中、改变动作、被修订或造成伤害；
- 两者互补，不能用个案替代总体指标，也不能用均值隐藏机制失败。

## 9. 效率与时间保护

- 先完成 Mini，再启动 fullgame；不在运行中边发现基础 Bug 边长跑。
- 串行演化链不能并行；独立 seed、独立消融或离线标注可以并行。
- 不通过删减完整上下文、卡牌信息或轨迹证据来加速。
- 每次实验启动前打印预计调用量、已有经验数、预期暴露条件和输出目录。
- 每幕只做预注册的系统审计，不临时增加语义规则。
- 发现问题先分类为系统 Bug、提示词问题、模型能力问题或实验设计问题；分类前不改代码。
- 一个阶段连续两次因同类系统问题失败，停止长跑并回到 Mini。
- 一旦计划外代码开始增加枚举、正则、兼容矩阵或特殊游戏知识，立即停工并报告。
- 如果 Baseline 自身偏差使 treatment 无法独立归因，终止该实验并保留诊断；不得通过修改 Baseline 来迁就记忆章节。

下一轮实施的计划时间盒：

| 阶段 | 计划上限 | 超时处置 |
|---|---:|---|
| Phase 1 系统契约测试 | 90 分钟 | 缩减到最关键契约，不增加语义测试 |
| Phase 2 就地瘦身 | 3 小时 | 停止编码，列出仍纠缠的公开接口与最小替代范围 |
| Phase 3 Mini 闭环 | 90 分钟 | 不启动 fullgame，决定继续缩减或放弃本章节 |

从获批到 Mini Go 的总上限为一个不超过 6 小时的集中工作段。超过上限仍未闭环时，必须向用户交付失败点和去留建议，不能静默继续到第二天。Fullgame 的 API 等待时间不计入编码时间盒，但只有 Mini Go 后才允许产生。

## 10. 下一轮讨论需要确认的四项选择

1. 默认使用 `single_pass`，还是把同模型 `critic_pass` 作为最小正式方法；
2. Active 的审视频率是每次相关战斗、每幕还是仅整局；
3. 通用经验是维护一份版本化短策略，还是与其他经验一样按键检索；
4. Phase 4 两局 Pilot 通过后，是否立即进入连续五局 Case Study，还是先做一次 RQ1 离线抽取比较。

在这四项得到确认前，不进入实现阶段。

## 11. 本计划的完成定义

本文档得到用户批准后，下一目标才能开始实施。实施目标只有在以下条件同时满足时才可结束：

- 最小链路通过 Mini；
- Baseline 和完整上下文未改变；
- Python 不再承担经验语义裁判；
- 所有模型错误可追踪、可分析；
- 真实在线自然暴露至少出现一次并完成后续审视；
- 已明确决定是否进入连续五局和三项正式研究。
